The thesis

Discogs built the world's deepest public music catalog. Every artist, label, release, pressing, format, credit - decades of obsessive human knowledge, structured and queryable. But it's a marketplace first. The API docs haven't changed since 2011. No agent-ready layer exists on top of it.

Dig builds that layer. REST API and MCP server over a normalised canonical database, fully open, no keys. Then a human search product on top of the same retrieval core. Then editorial - curated crates from people who actually know, context that feeds back into what agents can do.

Infrastructure first. Product second. Editorial compounds it over time.

Why the build order matters

The retrieval core is the product. Everything else - the REST API, the MCP tools, the human UI, the crates - is a different interface on top of the same thing. Build that once, build it correctly, and everything downstream gets cheaper and easier to trust.

Agent layer comes before human UI deliberately. Agents give you immediate utility with far less surface area to build and maintain. The human search product arrives later but uses identical endpoints - so UI and agent outputs are always aligned, and you never end up with two products running divergent logic.

The moat is data quality and retrieval correctness. Not front-end polish.

What "agent-first" actually means

Not an LLM product.
Not a chatbot.

It means deterministic retrieval infrastructure that agents can rely on before any polished UI exists.

The build
Phase 0

Data decisions

Nothing else starts until this is done. Profile real Discogs dump samples. Write the normalisation dictionary - ANV handling, track position encoding, credits nesting, master/release linkage. Lock schema v1. Define provenance fields and response shape conventions. Deliverable: Normalisation Dictionary v1. Schema v1 signed off.

Phase 1

Ingestion and canonical database

Dump batch tracking. XML parser into ingest.raw_entities. Canonical upserts - artists, labels, masters, releases, tracks, credits. QA reports covering counts, broken references, malformed values. Raw payload staging is non-negotiable. Deliverable: Repeatable import run on sample dataset. Canonical DB populated and queryable.

Phase 2

Retrieval core

Postgres FTS and pg_trgm for search. Entity lookup services. Relationship traversal - artist to releases, label to catalog, credits to works. Provenance and confidence fields on every response. Rate limiting and logging. Stable JSON contracts. Deliverable: Internal retrieval service layer. Stable contracts ready for API surface.

Phase 3

REST API and MCP public alpha

REST endpoints - /search, /releases/:id, /artists/:id, /labels/:id, /masters/:id, /releases/:id/media-links. MCP tools - search_catalog, get_release, get_artist, get_label, get_related_releases, explain_relationships, create_crate_draft. Docs and examples for Claude, ChatGPT, and standard LLM tooling. Deliverable: Agent-usable public alpha. Zero-friction REST endpoint and open MCP server.

Phase 4

Human search UI

Mobile-first search. Result pages for artists, labels, releases, masters. Cross-linked navigation - click anything, follow the thread. Performance tuning and caching. Same REST responses as the agent layer so nothing diverges. Deliverable: Usable human product on top of proven retrieval core.

Phase 5

Curation, crates, editorial

Curator profiles. Crate and list pages. Editorial notes with provenance. Linkouts to Spotify, Apple Music, Bandcamp, Discogs. Approved contributors only - selectors, label heads, engineers with something real to say. Context that feeds back into what agents know. Deliverable: Differentiated human layer. Agent context that compounds over time.

Risks worth naming
  • 01Data quality - everything inherits whatever the normalisation gets wrong. This is why Phase 0 is non-negotiable.
  • 02API abuse - fully open means rate limiting from day one, per IP, generous enough for legitimate use, tight enough to stop a runaway agent taking down the database.
  • 03Platform terms - Discogs CC0 dumps are clean. Spotify and Apple Music linkouts are referral, not data extraction. Bandcamp same. Stay on the right side of each.
  • 04Retrieval correctness - a wrong answer delivered confidently is worse than no answer. Provenance and confidence fields are not optional.

Non-goals

Marketplace. Compliance stack. Discogs write-back dependency. Open public editing. LLM proxying - Dig serves data, users bring their own models.

API + MCP

LLMs orchestrate. Dig retrieves. Every tool output is structured, reproducible, and explainable. MCP and REST call the same retrieval services. No hidden writes - agent tools read, rank, and explain by default.

Core retrieval API (REST)

  • GET /search (catalog entities + filters)
  • GET /artists/:id
  • GET /labels/:id
  • GET /masters/:id
  • GET /releases/:id
  • GET /releases/:id/media-links
  • GET /curators/:slug, /lists/:slug
