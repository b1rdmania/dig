Technical White Paper / Draft

Dig as an AI-first music discovery layer

An LLM-native discovery layer built on the most comprehensive structured music catalog available. Dig turns public Discogs catalog data into something humans and agents can search, reason over, and build with.

This document describes the product thesis, the AI retrieval architecture, the data normalization approach, and a risk-first implementation plan for a 1-2 person build.

1. Thesis & Product Shape

Scope-first

An AI layer over the deepest music catalog dataset.

Dig should be positioned as an AI-first, LLM-native music discovery layer built on public Discogs catalog data. The product value is not just a better UI, but a programmable intelligence layer: structured facts, explainable discovery, and curation-ready tools for humans and agents.

Core wedge: the AI discovery layer on top of collector-grade metadata, with API/MCP access, explainable graph retrieval, and curated crates. Avoid payments, KYC, tax, and marketplace compliance in v1.

This is

  • Deep music search
  • An AI/LLM discovery layer over music metadata
  • Curation tooling for DJs / radio / labels
  • A programmable music metadata layer
  • A bridge to streaming via matching/export

This is not

  • A marketplace rebuild
  • A streaming service
  • An AI that guesses or hallucinates
  • A dependency on Discogs write-back

2. Technical Decisions (Revised)

Defensible defaults
Modular Monolith First

Single deployable with clean domain boundaries. Fast to ship, low ops burden, easy to refactor after the schema and ingestion rules stabilize.

Postgres Search Before OpenSearch

Start with tsvector + pg_trgm and measure. Defer a dedicated search cluster until relevance/latency/product complexity requires it.

Raw Payload Staging Is Non-Negotiable

Store parsed Discogs entities in ingest.raw_entities before normalization. This protects re-derivation when importer logic and schema evolve.

Editorial-Only Auth in v1

No public user accounts initially. This keeps the product and legal surface small while supporting catalog, curation, and MCP/API features.

No LLM Proxying in v1

Expose API + MCP and let users/partners bring their own model runtime. Dig focuses on deterministic graph/search retrieval, not inference hosting.

3. Architecture

Mermaid

AI retrieval layer with a human UI on top

Dig is built as a shared retrieval core for both humans and LLMs: a mobile-first web app for browsing, plus an MCP/API layer that exposes structured catalog and curation tools for agent workflows.

Why this architecture fits an LLM-native product

  • One retrieval core powers both the UI and agents, which keeps behavior consistent and explainable.
  • One codebase keeps iteration speed high while the data model and tool surface are still evolving.
  • Search can start in Postgres and graduate later without changing the API/MCP contracts.

4. Data & Normalization Strategy

Load-bearing

Raw-first ingestion with a normalization dictionary

Before importer implementation, profile real dump samples and lock normalization rules in a living data dictionary. This prevents importer churn and schema thrash.

Pre-code requirement: write the Normalization Dictionary v1 from real dump samples, not assumptions. The three areas most likely to ripple through the schema are ANV handling, track position parsing, and credits/role encoding.
flowchart LR A["Discogs XML Dump"] --> B["Batch Record (dump_batches)"] B --> C["XML Stream Parse"] C --> D["Raw Staging (raw_entities)"] D --> E["Normalize / Validate"] E --> F["Canonical Catalog Tables"] F --> G["Search Documents (Postgres FTS)"] F --> H["Curation + Media Links"] F --> I["Matching / Export (later)"]

Normalization principles (v1)

  • Preserve raw source strings for messy fields (credits.role, identifiers, track positions).
  • Parse conservatively and keep helper columns nullable (e.g. released_year, duration_seconds).
  • Store ANV at relationship level, not as a global artist alias by default.
  • Treat master/release linkage as backfillable (do not block release imports on import order).

Schema shape already prepared

  • ingest.dump_batches + ingest.raw_entities for provenance and replayability
  • catalog.* tables for normalized entities and relationships
  • catalog.search_documents as a DB-side search substrate
  • media.*, curation.*, integration.* for later stages

5. Agent Interface (API + MCP)

Agent-first layer

LLM-native interface, deterministic retrieval underneath

Dig should expose structured retrieval and crate-building primitives via REST and MCP. LLMs can orchestrate the workflow, but the underlying retrieval layer should remain deterministic, inspectable, and explainable.

Core retrieval API (REST)

  • GET /search
  • GET /artists/:id
  • GET /labels/:id
  • GET /masters/:id
  • GET /releases/:id
  • GET /releases/:id/media-links
  • GET /curators/:slug
  • GET /lists/:slug

LLM-facing MCP tools

  • search_catalog
  • get_release / get_master_release
  • get_artist / get_label
  • get_related_releases
  • get_media_links
  • create_crate_draft (read-only suggestion mode)
  • explain_relationships

Agent interface design rules

  • Return provenance and confidence fields whenever results are inferred or matched.
  • No hidden side effects by default: tools should read, rank, explain, or draft unless explicitly authorized to write.
  • Keep MCP backed by the same retrieval/domain services as REST so humans and agents get the same facts.

6. Cost & Monetization (Technical View)

Pragmatic

Keep costs low by making retrieval deterministic

The main infrastructure costs are Postgres, background jobs, and API hosting. Costs only spike early if Dig becomes an LLM proxy. The current strategy explicitly avoids that.

Cost control principles

  • Use Postgres FTS before running a dedicated search cluster.
  • Let users bring their own model runtime for agent orchestration.
  • Cache common searches and async heavy jobs (imports, link checks, exports).
  • Defer streaming export matching until core catalog + curation are proven.

Monetization paths (compatible with architecture)

  • B2B API / Agent API: tiered access to search, graph, curation data
  • Pro curator tools: private crates, collaboration, export utilities
  • Media/editorial partners: branded curation pages and embeds
  • Consumer premium (later): advanced filters, saved lists, agent credits

7. Implementation Plan (1-2 People)

Risk-first

Do the hard thinking before code, then ship in milestones

  1. Pre-M0: Data profiling + normalization dictionary
    Sample real Discogs dump records and validate normalization decisions for ANV, track positions, credits, identifiers, master/release linkage.
  2. M1: Ingestion foundation
    Schema migrations, dump_batches, raw_entities, parser pipeline, canonical upserts, QA counts.
  3. M2: Search + read API
    Postgres FTS + pg_trgm, search endpoint, entity endpoints, index tuning, basic mobile read UI.
  4. M3: Curation + media links + editorial tooling
    Curators/lists, media links + provenance + validation job, admin/editorial flow.
  5. M4: MCP layer
    Deterministic MCP tools backed by shared domain services, API keys / rate limits if needed.
  6. M5: Matching/export beta (optional)
    External catalog candidate store, confidence scoring, export jobs, review UI.
  7. M6: Search cluster decision gate
    Only evaluate OpenSearch if metrics and product requirements justify it.

Non-goals to protect the build

  • No marketplace/compliance stack in v1
  • No public user accounts in v1
  • No LLM proxy billing / passthrough complexity
  • No dependency on Discogs writeback APIs for core functionality
